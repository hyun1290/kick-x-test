# 다음 개발 단계와 팀 결정표

기준: 2026-10-01. 먼저 실제 회원이 로그인하고, 실제 선수 정보를 읽고, 관심 선수를 저장하는 흐름을 완성합니다. 거래 규칙이 미정이어도 이 단계는 진행할 수 있습니다.

## 순서와 완료 기준

| 순서 | 할 일 | 완료 기준 |
| --- | --- | --- |
| 1 | Supabase에 초기 SQL 적용, Google 공급자/콜백 설정, Vercel 환경변수 등록 후 연결 활성화 | 로그인 → 프로필 등록 → 새로고침 → 로그아웃/재로그인에서 정보 유지 |
| 2 | API-FOOTBALL의 소수 실제 응답을 확인하고 필요한 지표/누락/경기 상태 매핑 확정 | 선수·구단·리그·경기 원본과 화면 표시가 일치 |
| 3 | 수집 작업·외부 ID upsert·수집 이력 구현, 화면별 검색/페이지네이션으로 조회 분리 | 하루 호출 예산 안에서 동작, 중복 적재 없음, 대량 목록·상세 응답 제한 확인 |
| 4 | Performance·가격·거래·포인트 정책 승인 | 표의 미정 항목과 예시 계산 결과를 팀이 문서화 |
| 5 | 원장·지갑·보유·거래 테이블과 서버 원자적 정산 구현 | 최초 지급 1회, 동시 주문/중복 요청/잔액 부족/가격 변경/실패 복구 검사 통과 |
| 6 | Performance/가격 계산·규칙 버전·이력·경기 정정/재계산 구현 | 같은 경기 재처리로 중복 가치 변화가 없고 정정 전후 이력 보존 |
| 7 | 자산 조회와 스쿼드 저장 연결 | 재접속해도 유지, 미보유/중복/11명 초과/포지션 위반 거부 |
| 8 | 자산 스냅샷과 주간/월간 랭킹 | 기간/동률/신규 회원 규칙으로 재현 가능한 집계 |
| 9 | 커뮤니티·첨부·댓글·공감·신고, 관리자 운영 | 타인 글/거래 첨부 거부, 응원 구단 권한 검사, 운영 감사 기록 |
| 10 | 실제 기록 기반 AI 설명과 배포 통합 시험 | 원천 기록/생성 시각 추적, 값의 임의 생성 없음, 로그인→거래→저장 시나리오 증빙 |

5·6단계는 서로 의존합니다. 실제 주문 확정은 가격 계산과 정산 검증이 모두 끝난 뒤 활성화합니다. 수집의 무료 호출 한도와 사용 중인 호스팅 제한은 프로젝트 계정에서 다시 확인해야 합니다.

| AI | 실제 기록을 설명하는 보조 기능 | 필수 여부, 생성 시점/주기, 무료 실행 방식 |

닉네임 2–20자와 선택형 응원 구단은 이번 코드의 기술적 입력 기본값입니다. 최종 운영 정책으로 확정한 것은 아닙니다. 거래 수수료 2%, 최초 잔액, 선수당 1명, 기본 포메이션, Performance 100점 만점 등은 임의로 지정하지 않았습니다.

## 첫 실제 데이터 적재 때 주의할 구조

- API의 외부 ID를 external_id에 보존하고 사이트용 id 매핑을 고정합니다.
- leagues → teams → players → fixtures 순서로 참조 관계를 맞춥니다.
- 미제공 수치는 NULL로 두고 0과 구분합니다.
- player_market_snapshots는 계산 결과 표시용이며 계산 엔진이 아닙니다. price/performance를 채울 때 각각 규칙 버전이 필요합니다.
- price_history와 player_match_records의 고유 제약만으로 수집/계산 재처리가 모두 완성되는 것은 아닙니다. 작업 키·시도/정정 이력을 추가해야 합니다.
- 분석 body는 실제 기록을 확인한 설명만 저장합니다.
- 공개 카탈로그는 누구나 읽을 수 있으므로 개인정보나 운영 비밀을 넣지 않습니다.

## 외부 설정이 끝난 뒤의 실제 시험

계정 A/B로 서로의 프로필과 관심 목록이 격리되는지, Google 취소/만료 후 재로그인이 가능한지, 네트워크 실패 후 저장 결과를 확인할 수 있는지, 실제 데이터가 0/null일 때 화면에 정확히 표시되는지 확인합니다. CI의 주입 응답과 임시 PostgreSQL 검사는 이 운영 통합 시험을 대신하지 않습니다.

Yellow Playbook 레퍼런스 이미지는 직접 확인했습니다. 첨부 수정3(1).docx는 파일을 불러올 수 없었으므로 이 구현/결정표와 다시 대조해 문서 고유의 추가 요구사항을 확인해야 합니다.
