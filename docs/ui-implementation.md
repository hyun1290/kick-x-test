# KICK-X 페이지별 기능과 개발 인수인계

작성 기준: 2026-09-28, 제공된 요구사항 정의·분석 명세서 2종과 프로젝트 제안서, 기존 20개 페이지 구조.

## 이번 변경의 범위

기존 예시 선수·구단·리그·경기 일정·경기 기록·가격과 그래프·자산·거래·순위·회원·게시글·댓글·신고·관리자 작업 이력을 모두 제거했습니다. 초기 포인트와 선수 지급, 자동 로그인, 로컬 거래/저장/운영 시뮬레이터도 제거했습니다. 미확정인 수수료 2%, 선수당 1명 보유, 특정 포메이션 목록과 기본 선택을 운영 정책으로 남겨두지 않았습니다.

기존 20개 URL, 네이비·블루 디자인, 경기장 장식 이미지, 한글 글꼴과 반응형 레이아웃은 유지합니다. 알 수 없는 금액·순위는 `—`, 목록·표·그래프는 빈 상태입니다. 차트에는 DB에서 받은 시각과 값만 사용합니다. 로그인 사용자가 없을 때 가상의 닉네임·잔액·순위를 만들지 않습니다.

**현재 가능한 것:** 페이지 이동, 탭·검색·필터·정렬·보기 전환, 빈 상태 확인, 입력 양식 확인. 향후 서버 조회 결과가 들어오면 해당 데이터로 목록/차트/상세가 표시됩니다. 조회된 보유 선수와 포메이션이 있을 때 스쿼드의 임시 편집/되돌리기도 가능합니다.

**현재 불가능한 것:** 실제 로그인·회원 등록, 데이터 영구 저장, 주문 확정, 관심 선수 저장, 게시글/댓글 등록·수정·삭제, 신고 처리, 운영 작업 재실행. 관련 버튼은 실제 쓰기 서비스 연결 전까지 완료 처리되지 않습니다. 입력 중인 내용은 DB나 브라우저 저장소에 저장하지 않습니다.

## 이미 자료에 정해진 원칙

- 가상 포인트를 사용하며 실제 선수의 이적·소속 구단 변경과 게임 내부 보유는 구분합니다.
- Performance와 거래 가격을 구분하고 계산 규칙 버전을 기록합니다.
- 선수단은 **보유 선수 중 최대 11명**, GK/DF/MF/FW 포지션을 기준으로 구성합니다.
- 초기 포인트는 최초 한 번만 지급하며 재로그인으로 중복 지급하지 않습니다.
- 구단 커뮤니티 작성 권한은 응원 구단에 따라 결정하며 타인의 거래 내역을 첨부할 수 없습니다.
- 게시글·댓글의 수정/삭제는 작성자 또는 관리자 권한으로 검증합니다.
- 거래와 경기 데이터 재처리는 중복 반영을 막고, 당시 가격·수수료·정산액과 계산/운영 이력을 보존합니다.
- AI 분석을 넣는 경우에도 실제 기록을 설명하는 보조 기능이며 가격이나 원천 경기 수치를 임의로 정하지 않습니다.

아래의 ‘결정할 사항’은 이 원칙을 없애자는 뜻이 아니라 아직 구체화해야 할 기준입니다. 두 명세서의 포함 범위에 차이가 있는 AI 분석 등은 최종 제출본/개발 범위를 하나로 통일해야 합니다.

## DB를 연결하는 위치

화면 → `PlatformProvider` → `GET /api/kickx` → `readPlatform()` → `KickxRepository` 순으로 조회합니다. 운영 화면은 `useAdminData()`와 `GET /api/kickx/admin`을 별도로 사용합니다.

1. Supabase 테이블과 관계·고유키·RLS 정책을 먼저 설계합니다.
2. `server/kickx/` 아래에 실제 서버 전용 어댑터를 구현합니다. `getSession()`에서 검증한 세션만 회원·관리자 판단에 사용합니다.
3. `getPublicData()`에는 공개 가능한 선수·시세·일정·게시글·랭킹만 반환합니다. 숨김/삭제 콘텐츠와 비공개 계정 정보는 서버 조회 단계에서 걸러야 합니다.
4. `getMemberData(userId)`에는 해당 사용자의 잔액·보유·거래·선수단만 반환합니다. 사용자 ID는 요청 파라미터가 아니라 검증된 세션에서 전달됩니다.
5. `getAdminData()`에는 실제 관리 권한을 확인한 뒤에만 접근합니다. 현재 서비스의 401/403 차단 구조를 유지합니다.
6. `getKickxRepository()`의 미연결 어댑터를 구현한 어댑터로 교체합니다. **아직 실제 구현이 없는 상태에서 `configured`만 true로 바꾸면 안 됩니다.**
7. 저장 기능별 서버 API를 구현하고 권한·입력·원자성을 검증한 다음 비활성 버튼을 연결합니다. 응답 확인 후 화면을 다시 조회하며 클라이언트 계산으로 잔액을 확정하지 않습니다.

현재 인터페이스는 초기 연결을 쉽게 확인하는 전체 조회 구조입니다. 서비스 데이터가 쌓이기 전에 목록·상세·댓글·랭킹을 필요한 범위로 나누고 서버 페이지네이션/검색으로 전환해야 합니다. 거래 첨부는 공개할 필드만 선별하고 사용자/계정 내부 정보는 넣지 않습니다. `types.ts`는 화면 표시 형태이므로 그대로 하나의 큰 DB 테이블로 만들지 않습니다.

## 먼저 결정할 핵심 정책

1. **거래 구조:** 시스템 상대 즉시 거래인지 사용자끼리 주문을 맞추는지, 여러 사용자의 동일 선수 보유를 허용하는지, 한 계정이 같은 선수를 몇 단위 보유할지. DB 설계에 가장 먼저 영향을 줍니다.
2. **초기 포인트와 가격:** 최초 지급액, 선수 초기 가치 산정, 최저/최고 가격과 포인트 정밀도, 신규 선수·장기 미출전·리그 이탈 처리.
3. **Performance:** 포지션별 지표와 가중치, 팀 기여·클린시트 반영, 미출전/누락/퇴장 처리, 실제 API에서 확보 가능한 지표. 임의의 100점 만점도 전제하지 않았습니다.
4. **가격 변동:** 평가 기간, Performance→가격 변환식, 상승/하락 제한, 수요 반영 여부, 반영 시점과 정정 계산. 경기 점수와 가격을 구분합니다.
5. **판매 수수료:** 적용 여부/기본 요율, 거래량 구간별 추가 요율, 거래량 집계 기간, 반올림/절사와 정산 규칙. 이전의 2%는 제거했습니다.
6. **선수단:** 최대 11명 안에서 허용 포메이션, 빈 자리, 다중 포지션, 선수 매각/실제 이적 시 처리.
7. **자산·랭킹:** 원가와 손익, 수익률 분모, 주간/월간 기간과 동률, 신규 회원 참가, 시즌이 바뀌어도 유지할 데이터.
8. **커뮤니티·운영:** 닉네임과 응원 구단 변경 제한, 작성/조회/댓글 권한, 신고·숨김 절차, 관리자 지정. 상세 작성 제한은 UI가 아닌 서버에서도 적용해야 합니다.
9. **개발 범위:** AI 분석을 필수로 할지, 데이터 확보/거래/선수단을 먼저 완성한 뒤 추가할지 최종 문서와 통일합니다.

## 이번 변경의 검증 결과

- `npm run build`: 20개 화면과 조회 API 2개 빌드 및 타입 검사 통과.
- `npm run lint`, `npm test`: 린트와 데이터 경계 테스트 8개 통과.
- 실제 브라우저: 20개 경로의 빈 상태, 데스크톱/모바일 레이아웃, 예전 데모 저장소 제거, 조회 오류·재시도, 비활성 쓰기 동작, 연결 응답의 0/null 표시, 수정 양식 초기화, 관리자 접근 거절 등 9개 검사 묶음 통과. 최종 실행의 JavaScript 오류 없음.
